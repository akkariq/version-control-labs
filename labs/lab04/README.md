## СКВ · Часть 1. Reset, revert, restore и amend

### СКВ · Подготовка и три режима reset

От начальной main (ad7021c) создана feature/experiment. Исходные коммиты: f1b3593 — file1.txt, 3a8a12d — file2.txt, 1163d17 — file3.txt. Ветка отправлена до reset, чтобы существовала ссылка origin/feature/experiment для восстановления по методичке.

<details>
<summary>Команды отмены и фактические результаты</summary>

```
git push -u origin feature/experiment
git reset --soft HEAD~1
git diff --quiet origin/feature/experiment && git reset --hard origin/feature/experiment
git reset --mixed HEAD~1
```

После soft reset file3.txt оставался в индексе. Проверка diff перед восстановлением сравнивала рабочее содержимое с серверным коммитом; возврат выполнен на 1163d17. После mixed reset HEAD переместился на 3a8a12d, а file3.txt стал неотслеживаемым.

```
echo "Четвёртый коммит" > file4.txt
git add file4.txt
git commit -m "feat: add file4"
git diff --quiet HEAD && git reset --hard HEAD~1
```

Создан 55727fc. Проверка diff не обнаружила незакоммиченных изменений отслеживаемых файлов; hard reset вернул HEAD на 3a8a12d. Проверки ls и test подтвердили: file4.txt исчез, file3.txt сохранился. Такая проверка не является общей защитой любых untracked-файлов: hard reset может затронуть неотслеживаемые пути, мешающие восстановлению.

</details>

### СКВ · Revert и restore

<details>
<summary>Команды и подтверждённые состояния</summary>

```
echo "Важные данные" > data.txt
git add data.txt
git commit -m "feat: add important data"
echo "Испорченные данные" > data.txt
git add data.txt
git commit -m "fix: corrupt data"
git revert HEAD --no-edit
cat data.txt
```

0792cad добавил данные, 545d781 испортил их, 1f7e565 создал обратный коммит. Вывод cat: «Важные данные». Коммит порчи остался в истории.

```
git restore data.txt
cat data.txt
echo "Ещё изменения" >> data.txt
git add data.txt
git diff --cached -- data.txt
git restore --staged data.txt
git diff -- data.txt
git diff --cached -- data.txt
```

После восстановления показана строка «Важные данные». Начальное добавление строки «Новые изменения» в присланном фрагменте отсутствует, поэтому полный первый цикл restore отдельно не подтверждён. Второй цикл подтверждён: добавленная строка сначала находилась в индексе, после restore --staged осталась только в рабочем файле (статус « M data.txt», cached diff пуст). Перед следующей практикой отслеживаемые изменения устранены; итоговый status показывал только file3.txt.

</details>

### СКВ · Исправление последнего коммита

В app.py создан учебный текст, не исполняемая Python-функция. Коммит 5013802 имел сообщение feat: add app fumction. Команда git commit --amend -m "feat: add app function" заменила его на 4465086. Затем содержимое app.py заменено строкой «# Модуль приложения» и включено в коммит через amend --no-edit.

```
echo "# Модуль приложения" > app.py
git add app.py
git commit --amend --no-edit
```

Итог — d635b3d с прежним исправленным сообщением и родителем 1f7e565. Символ > заменил содержимое, а не добавил строку. Эти результаты подтверждены локально; feature/experiment после начальной публикации 1163d17 повторно не отправлялась и в main не сливалась.

## СКВ · Часть 2. Интерактивный rebase и GitLab

В feature/rebase_experiment от ad7021c создан file.txt: пять коммитов добавляли строки 1–5. Исходная цепочка: f2ede2c, 9cd8aa3, 8b00f72, 1db0b28, 0dd2f9a. Ветка отправлена до переписывания для последующей проверки отказа обычного push.

<details>
<summary>Подготовка и редактор</summary>

```
git switch main
git switch -c feature/rebase_experiment
for i in {1..5}; do
    echo "Строка $i" >> file.txt
    git add file.txt
    git commit -m "feat: add line $i" || break
done
git push -u origin feature/rebase_experiment
GIT_SEQUENCE_EDITOR=nano GIT_EDITOR=nano git rebase -i HEAD~3
```

Переменные редактора задавались для отдельной команды; постоянные настройки Git не менялись.

</details>

| Действие | Диапазон и выбор | Подтверждённый результат |
|---|---|---|
| reword | HEAD~3; последние три коммита | 46773ff, fb1dbbb, c4a9420 с сообщениями docs: update line 3/4/5 with description |
| squash | HEAD~5; второй и третий объединены с первым | 5c264d7 сохранил три исходных сообщения; оставшиеся коммиты — 0f78e43 и cac78ec |
| drop | HEAD~3; исключён последний cac78ec | Два коммита над main, только строки 1–4 |
| edit | HEAD~2; выбран второй 0f78e43 | Остановка, изменение файла, amend и продолжение; новая вершина c73b887 |

<details>
<summary>Изменение при edit и публикация</summary>

```
echo "Изменённая строка 1" >> file.txt
git add file.txt
git commit --amend --no-edit
git rebase --continue
git push origin feature/rebase_experiment
git push --force-with-lease origin feature/rebase_experiment
```

Обычный push отклонён с non-fast-forward. Force-with-lease выполнил forced update 0dd2f9a → c73b887. Команда >> добавила строку в конец; исходная строка 1 не заменялась. После обработки осталось два коммита над начальной main: 5c264d7 и c73b887.

</details>

MR !1 «docs: merge interactive rebase experiment» создан и слит студентом в браузере. До слияния API подтвердил отсутствие конфликтов и единственный новый file.txt с пятью строками: «Строка 1»–«Строка 4», «Изменённая строка 1». Merge-коммит fc5d929 имеет родителей ad7021c и c73b887. Squash при слиянии не применялся, исходная ветка сохранена. Локальная main обновлена через git pull --ff-only origin main.

<details>
<summary>Замена последнего коммита и первая публикация</summary>

git status --short
git diff --cached -- clean_history.txt
git commit -m "feat: finalize clean history example"

</details>

### СКВ · Удаление учебного файла из истории

<details>
<summary>Локальный коммит и filter-branch</summary>

```
echo "password=123" > secret.txt
git add secret.txt
git commit -m "fix: add secret"
git filter-branch --force --index-filter "git rm --cached --ignore-unmatch secret.txt" --prune-empty
```

password=123 — фиктивная заглушка методички, не реальный пароль. Коммит 35ad57f существовал только локально. Filter-branch вывел предупреждение и обработал десять достижимых коммитов, включая предков main; изменена ссылка только текущей ветки. После удаления secret.txt коммит 35ad57f стал пустым и исключён. HEAD вернулся на cd32bab.

```
git rev-list --count main..HEAD
git log --oneline HEAD -- secret.txt
test ! -e secret.txt && echo "OK: secret.txt отсутствует"
```

Подтверждены пять коммитов над main, пустой вывод истории для secret.txt и отсутствие файла. Это очистка достижимой истории ветки, не физическое уничтожение всех копий: refs/original и reflog локально не очищались.

</details>

## СКВ · Контрольные вопросы

<details>
<summary>1. В чём разница между reset и revert? Когда что использовать?</summary>

Reset в форме с коммитом перемещает вершину ветки; режим определяет состояние индекса и рабочего каталога. Revert создаёт новый коммит обратных изменений, сохраняя исходную историю. Reset подходит для редактирования собственной локальной истории, revert — для отмены опубликованных изменений общей ветки.

[Reset](https://git-scm.com/docs/git-reset) · [Revert](https://git-scm.com/docs/git-revert)

</details>

<details>
<summary>2. Что делает reset --hard и почему это опасно?</summary>

Он перемещает HEAD, восстанавливает индекс и рабочие файлы из выбранного коммита. Незакоммиченные изменения отслеживаемых файлов могут быть потеряны. Untracked-пути, мешающие восстановлению, также могут быть удалены или перезаписаны; это не универсальная команда удаления всех неотслеживаемых файлов.

[Документация](https://git-scm.com/docs/git-reset)

</details>

<details>
<summary>3. Какие действия доступны в интерактивном rebase?</summary>

Pick применяет коммит; reword меняет сообщение; edit останавливает процесс для изменения или разделения коммита; squash объединяет с предыдущим с редактированием сообщения; обычный fixup объединяет, отбрасывая сообщение текущего; drop исключает коммит; exec запускает команду оболочки. Можно менять порядок строк списка.

[Документация](https://git-scm.com/docs/git-rebase)

</details>

<details>
<summary>4. Как объединить коммиты с сохранением сообщений?</summary>

Запустить интерактивный rebase нужного диапазона, оставить pick у первого и поставить squash у следующих. В редакторе сохранить или отредактировать общее сообщение. В работе первые три коммита объединены в 5c264d7 с сохранением сообщений.

[Документация](https://git-scm.com/docs/git-rebase)

</details>

<details>
<summary>5. Как изменить сообщение последнего коммита?</summary>

Git commit --amend -m "Новое сообщение" заменяет последний коммит новым, а не добавляет обычный следующий. Подготовленные изменения индекса тоже входят в заменяющий коммит; перед операцией нужно проверить индекс. Для включения изменений без смены сообщения применяется --amend --no-edit.

[Документация](https://git-scm.com/docs/git-commit)

</details>

<details>
<summary>6. Почему push --force опасен?</summary>

Он отключает обычную проверку fast-forward и позволяет заменить удалённую историю. Чужие коммиты, отсутствующие в локальной версии, могут перестать быть достижимыми от ветки. Переписывание общих веток без согласования недопустимо.

[Документация](https://git-scm.com/docs/git-push)

</details>

<details>
<summary>7. Чем force-with-lease лучше обычного force?</summary>

Он проверяет ожидаемую вершину серверной ветки. Без дополнительных параметров ожидание берётся из соответствующей локальной remote-tracking ссылки. При несовпадении push отклоняется. Это дополнительная проверка, не универсальная гарантия: фоновый fetch может изменить локальное ожидание; при необходимости его задают явно через ref:expect.

[Документация](https://git-scm.com/docs/git-push)

</details>

<details>
<summary>8. Как восстановить коммит после reset --hard?</summary>

Найти прежнюю вершину через git reflog, проверить нужный коммит и создать на нём отдельную ветку восстановления. Это сохраняет найденную историю без нового reset текущей ветки. Восстановление зависит от доступности объектов; reflog не гарантирует возврат незакоммиченных изменений. В этой работе восстановление разобрано теоретически.

[Документация](https://git-scm.com/docs/git-reflog)

</details>

<details>
<summary>9. Когда использовать revert, а когда reset?</summary>

Revert — для отмены опубликованных изменений без замены общей истории. Reset — для перемещения собственной локальной ветки и изменения состояния индекса или рабочего каталога: soft сохраняет индекс и файлы, mixed сбрасывает индекс, hard восстанавливает и индекс, и рабочие файлы.

[Reset](https://git-scm.com/docs/git-reset) · [Revert](https://git-scm.com/docs/git-revert)

</details>

<details>
<summary>10. Почему не следует делать rebase общих веток?</summary>

Rebase создаёт новую последовательность коммитов. Если другие участники уже работают на прежней истории, её замена приводит к расхождению историй и усложняет интеграцию. Опубликованную общую историю не переписывают без координации; здесь переписывались только собственные учебные feature-ветки.

[Документация](https://git-scm.com/book/en/v2/Git-Branching-Rebasing)

</details>
