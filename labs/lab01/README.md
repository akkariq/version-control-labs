## СКВ · Контрольные вопросы

<details>
<summary>1. Что такое распределённая система контроля версий и чем она отличается от централизованной?</summary>

В распределённой системе участники имеют локальные репозитории с историей. Обычный полный клон Git позволяет делать локальные коммиты и просматривать историю без постоянного обращения к серверу. В централизованной системе основная история находится на центральном сервере, а клиент обычно получает рабочую копию. В Git сервер используется для обмена изменениями, но локальный репозиторий остаётся самостоятельным.

[Документация](https://git-scm.com/book/ru/v2/Введение-О-системе-контроля-версий)

</details>

<details>
<summary>2. Для чего нужен SSH-ключ при работе с GitLab?</summary>

Пара ключей подтверждает право доступа при работе по SSH. Публичный ключ добавляют в GitLab, приватный защищают на своём устройстве. В данной работе проверка вернула Welcome to GitLab, @akkariq!. Приватный ключ и парольную фразу нельзя включать в публичный отчёт.

[Документация](https://docs.gitlab.com/user/ssh/)

</details>

<details>
<summary>3. В чём разница между git add и git commit?</summary>

git add помещает выбранное содержимое в индекс для следующего коммита. git commit сохраняет подготовленное содержимое индекса в локальном коммите. Правки, сделанные после git add, требуют повторного добавления, если их нужно включить в коммит. Эти команды не отправляют изменения на сервер: для этого нужен git push.

[Документация](https://git-scm.com/book/ms/v2/Git-Basics-Recording-Changes-to-the-Repository)

</details>

<details>
<summary>4. Что такое staging area (индекс) в Git?</summary>

Индекс — область подготовки следующего коммита. Он отделяет текущее содержимое рабочего каталога от выбранного набора изменений, который будет сохранён. Это позволяет объединять в коммит только логически связанные изменения.

[Документация](https://git-scm.com/docs/git-add)

</details>

<details>
<summary>5. Как проверить, какие файлы были изменены, но ещё не добавлены в коммит?</summary>

git status показывает подготовленные и неподготовленные изменения, а также новые неотслеживаемые файлы. git diff показывает различия рабочего каталога и индекса; git diff --cached — различия индекса и последнего коммита. Общую проверку удобно начинать с git status.

[Документация](https://git-scm.com/book/ms/v2/Git-Basics-Recording-Changes-to-the-Repository)

</details>

<details>
<summary>6. Для чего нужен файл .gitignore? Приведите примеры.</summary>

Он задаёт шаблоны файлов, которые не следует включать в отслеживание. В работе исключены .DS_Store, Thumbs.db, *.tmp, *.log, .vscode/ и .idea/. Правила не прекращают отслеживание уже закоммиченных файлов. При необходимости такой файл удаляют из индекса командой git rm --cached имя_файла и сохраняют изменение коммитом.

[Документация](https://git-scm.com/docs/gitignore)

</details>

<details>
<summary>7. Как связать локальный репозиторий с удалённым?</summary>

Добавляют адрес через git remote add origin git@gitlab.com:username/project.git и проверяют git remote -v. Первая отправка git push -u origin main задаёт upstream; затем можно использовать git push. В данной работе origin уже настроен, поэтому повторно добавлять его не нужно.

[Документация](https://git-scm.com/docs/git-remote)

</details>

<details>
<summary>8. Чем отличается git fetch от git pull?</summary>

git fetch получает объекты и обновляет соответствующие ссылки удалённого репозитория, не интегрируя автоматически изменения в текущую локальную ветку. git pull сначала выполняет fetch, затем интегрирует полученную ветку в текущую. Способ интеграции зависит от параметров и настроек, например merge или rebase.

[Документация](https://git-scm.com/docs/git-pull)

</details>
