## СКВ · Часть 2. Rebase и GitLab

### СКВ · Конфигурация базы данных

В feature/database создан config.txt со строками SQLite и PostgreSQL: исходный dbc966c. В main независимо добавлен вариант с MySQL: bcde007. git rebase main остановился на конфликте добавление/добавление:

```text
<<<<<<< HEAD
database: MySQL
=======
database: SQLite
database: PostgreSQL
>>>>>>> dbc966c (feat(db): add database configuration)
```

Выбран итоговый учебный текст:

```text
database: MySQL

```

После git add config.txt и GIT_EDITOR=true git rebase --continue коммит dbc966c заменён на 535861c поверх bcde007. Сам rebase merge-коммита не создал. Файл служит упражнению с Git, а не конфигурации приложения с одной активной базой.

### СКВ · MR !1 и релизный MR !2

Ветки опубликованы через git push --all origin. Студент в браузере создал и слил MR !1 из feature/database в main. Перед слиянием проверен diff: к MySQL добавляются только SQLite и PostgreSQL. Статус merged и merge-коммит a2c482c подтверждены API. Исходная ветка сохранена, squash выключен.

От обновлённой main создана release/v1.0, добавлен version.txt со строкой version: 1.0.0, коммит a138c69. MR !2 Release v1.0.0 создан и слит в браузере; проверены diff нового файла и merge-коммит f23815f. Исходная ветка сохранена, squash выключен.

<details>

### СКВ · Фичи и diff.txt

На этой ветке выполнено git diff HEAD~2 HEAD > diff.txt. Предоставленный вывод показывает добавление второй и третьей фич относительно состояния после первой:

```diff
@@ -6,3 +6,5 @@

 6. Система уведомлений

+вторая фича
+третья фича
```

### СКВ · Отмена и исправление

Выбран допускаемый методичкой revert. Отменены сначала вторая, затем первая учебные фичи. Исходная история и опубликованный релиз сохранены. Содержимое возвращено к состоянию перед двумя фичами, соответствующему f23815f.

```text
git switch main
git revert --no-edit 7a5e255
git revert --no-edit 1264ae1
echo "исправленная фича" >> features.txt
git add features.txt
git commit -m "feat: add corrected feature"
git add diff.txt
git commit -m "docs: save feature comparison in diff.txt"
```

Результаты: 5e10e6e и 8122edd — обратные коммиты, 638508a — исправленная фича, c25db92 — сохранённый diff.txt. Разницу намеренно не пересчитывали после отмены.

### СКВ · Повторный rebase и fast-forward

При git switch feature/third и git rebase main возник конфликт: исправленная фича против старых первой, второй и третьей. Оставлены исправленная и третья, отменённые строки не возвращены. После git add features.txt и GIT_EDITOR=true git rebase --continue ef57499 заменён на e7ed679 поверх c25db92.

Затем выполнены git switch main и git merge --ff-only feature/third. Фактический вывод: Fast-forward с c25db92 на e7ed679; дополнительный merge-коммит не создавался.

## СКВ · Уточнения к методичке

1. «К 3-му коммиту» и пример HEAD~3 неоднозначны. Фактически выбрана отмена двух новых учебных фич через revert с возвратом содержимого к f23815f. Буквальный reset --hard HEAD~3 не выполнялся.
2. Вместо release использована release/lab2-final: Git не допускает одновременно release и release/v1.0. Это объяснённое отличие от имени в задании, не заявление о буквальном совпадении.
3. diff.txt соответствует явно указанной команде HEAD~2 HEAD; её диапазон шире сравнения HEAD~1 и HEAD.
4. history.txt — снимок момента создания, без собственного последующего коммита 440b925.
5. VS Code опционален и отдельно не подтверждён. Упражнение release от main не является полной реализацией Git Flow с develop.
6. Успешный CI/CD и оценка преподавателя не заявлены. При требовании буквального сценария спорные пункты следует согласовать с преподавателем.

## СКВ · Контрольные вопросы

<details>
<summary>1. Что такое ветка в Git и как она реализована технически?</summary>

Ветка — подвижная ссылка на коммит, вершину линии разработки. Локальные ветки представлены refs/heads, HEAD обычно указывает на текущую ветку. Новый коммит продвигает её указатель. Создание ветки не копирует весь проект и не создаёт коммит.

[Документация](https://git-scm.com/book/ms/v2/Git-Internals-Git-References)

</details>

<details>
<summary>2. В чём разница между git merge и git rebase? Когда что применять?</summary>

Merge объединяет линии истории: fast-forward перемещает указатель, слияние расходящихся веток создаёт merge-коммит. Rebase заново применяет изменения выбранных коммитов поверх новой базы, меняя хеши. Merge удобен для опубликованных веток; rebase — для собственной ветки до публикации. В работе показаны оба подхода.

[Документация](https://git-scm.com/book/en/v2/Git-Branching-Rebasing)

</details>

<details>
<summary>3. Что такое конфликт слияния и как он возникает?</summary>

Git не может автоматически согласовать изменения, например разные правки одного участка или независимое добавление одного файла. В работе получены конфликт содержимого при merge и повторном rebase, а также добавление/добавление config.txt.

[Документация](https://git-scm.com/docs/git-merge)

</details>

<details>
<summary>4. Как разрешить конфликт вручную? Что означают маркеры?</summary>

Выбрать итоговый текст, удалить маркеры, выполнить git add. Merge завершается коммитом, rebase — git rebase --continue. Маркер <<<<<<< начинает первый вариант, ======= отделяет второй, >>>>>>> завершает его. При rebase HEAD относится к новой базе и уже применённым изменениям, второй вариант — к переносимому коммиту.

[Документация](https://docs.gitlab.com/topics/git/git_rebase/)

</details>

<details>
<summary>5. В чём отличие git reset от git revert? Когда какой использовать?</summary>

Reset перемещает указатель ветки; режим определяет влияние на индекс и рабочий каталог. --hard заменяет отслеживаемые файлы и может уничтожить незакоммиченные правки. Revert записывает новый коммит отмены, сохраняя старую историю. Для опубликованных изменений обычно предпочтительнее revert; именно он использован в работе.

[Документация](https://git-scm.com/docs/git-revert)

</details>

<details>
<summary>6. Что такое fast-forward и чем он отличается от трёхстороннего слияния?</summary>

Fast-forward возможен, когда текущий коммит является предком новой вершины: указатель перемещается без merge-коммита. При расходящихся линиях учитываются две вершины и общий предок, обычно создаётся коммит с двумя родителями. --no-ff требует отдельный merge-коммит; --ff-only отказывается от слияния, если fast-forward невозможен. В работе оплата слита с --no-ff, третья фича — с --ff-only.

[Документация](https://git-scm.com/docs/git-merge)

</details>

<details>
<summary>7. Зачем нужна ветка release в Git Flow?</summary>

Она отделяет стабилизацию релиза: исправления, обновление версии и документации. В классическом Git Flow release создают от develop, затем включают результаты в main и develop. В методичке применяется упрощённый пример release от main, не полный Git Flow.

[Документация](https://www.atlassian.com/git/tutorials/comparing-workflows/gitflow-workflow)

</details>

<details>
<summary>8. Как отправить все локальные ветки в удалённый репозиторий?</summary>

git push --all origin отправляет локальные ветки. Теги автоматически не отправляются: при необходимости используют git push --tags origin. Для upstream конкретной ветки — git push -u origin имя_ветки.

[Документация](https://git-scm.com/docs/git-push)

</details>

<details>
<summary>9. Почему rebase опасен на общих ветках?</summary>

Он создаёт новые коммиты вместо исходных. Если участники основали работу на старых, переписывание опубликованной истории усложняет синхронизацию. Безопаснее перебазировать собственные неопубликованные изменения. В работе оба rebase выполнены до первой отправки соответствующих веток, force-push не понадобился.

[Документация](https://git-scm.com/book/en/v2/Git-Branching-Rebasing)

</details>
